# Agrobudservices — Webflow → Next.js Migration

## Стек
- Next.js 14+ (App Router), TypeScript, Tailwind CSS
- Деплой: Vercel
- Контент: повністю статичний (без CMS), каталог (4 товари) і блог (2 пости) — TS/JSON у /src/content
- Шрифти: підключати через next/font/local з файлів у /legacy-export/fonts (НЕ через @font-face в CSS)
- Зображення: через next/image, з явними width/height (запобігає layout shift)

## Джерело правди
- Розмітка і контент оригінального сайту: /legacy-export (Webflow HTML export)
- НЕ копіювати баги і проблеми верстки 1-в-1 — оригінал містить проблеми з overflow,
  z-index, responsive поведінкою тощо. Під час перенесення кожної секції їх треба
  знаходити і виправляти самостійно, без окремого списку — оцінювати кожну секцію
  критично, як дизайнер/фронтенд-розробник, що робить сайт заново, а не копію

## Конвенції
- Один компонент = одна логічна секція сторінки (Hero, ProductGrid, ContactForm тощо)
- Спільні елементи (Header, Footer, Nav) — окремі переюзовувані компоненти в /src/components/layout
- Стилі — тільки Tailwind utility classes, кастомний CSS лише коли Tailwind не вистачає
- Усі інтерактивні елементи — перевіряти на overflow/z-index/responsive одразу під час перенесення

## UX/UI покращення (обов'язково при кожній секції)
Окрім точного перенесення функціоналу, активно покращувати UX/UI, не змінюючи бренд і
загальний стиль сайту:
- Плавні transition/hover-стани на кнопках, картках, посиланнях (якщо їх не було)
- Коректні focus-стани для доступності (клавіатурна навігація)
- Достатні touch-таргети на мобільній версії (мінімум ~44px для кнопок/лінків)
- Візуальна ієрархія: перевіряти контраст тексту, відступи (spacing), вирівнювання
- Анімації/переходи між станами не мають бути різкими або "стрибати"
- Забезпечити плавний адаптив без різких зламів layout між брейкпоінтами
- Якщо в оригіналі елемент виглядає переобтяженим чи заплутаним — пропонувати
  простіше рішення, зберігаючи зміст і функціонал

### Усталені патерни (використовувати на всіх сторінках)
Ці рішення вже прийняті на головній — нові сторінки мають брати їх, а не
вигадувати свої, інакше сайт розповзеться стилістично.

**Контейнер і ритм**
- Контент завжди в `container-page` (1280px + 20px бокових на всіх брейкпоінтах).
  Повноширинним може бути лише фон — його дає `<section>`, контент усередині
  все одно в контейнері
- Вертикальний ритм секцій — `py-15 md:py-20` (60/80px). Відхилення лише з
  явної причини і з коментарем у коді
- Хедер за замовчуванням `solid` (у потоці). Прозорий `overlay` — виняток лише
  для сторінок із повноекранним hero, спеціально розрахованим на це (нині лише
  головна, див. `OVERLAY_HEADER_ROUTES` у Header). Нову сторінку туди НЕ додавати:
  overlay накриє верх її першої секції

**Типографіка** (утиліти в globals.css, не задавати розміри вручну)
- `text-h1` — заголовок сторінки, `text-h2` — заголовок секції (усі однакові!),
  `text-h3`/`text-h4` — заголовки карток і підблоків
- `text-stat` — велика акцентна цифра золотим (статистика, показники)
- `text-eyebrow` — надрядкова мітка: дати, лейбли полів, секційні підписи
- Ключові цифри виносити з рядка тексту в окремий ключ messages (`value`),
  а не лишати всередині заголовка

**Scroll-reveal**
- Компонент `<Reveal>` з `@/components/ui/Reveal`: `variant="block"` для
  цілого блоку, `variant="stagger"` для сітки карток (каскад по черзі)
- Реалізація — CSS scroll-driven animations (`animation-timeline: view()`),
  серверний компонент, нуль JS у бандлі
- НІКОЛИ не вішати `Reveal` на `position: sticky` елемент або його предка —
  `translate` створює containing block і ламає прилипання
- Hero та інші блоки над згином не обгортати — вони й так одразу видимі

**Рух і анімації**
- Тільки CSS transitions/animations. Жодних анімаційних бібліотек:
  scroll-stacking, reveal і hover уже вирішені нативно
- Кожен рух дублювати варіантом `motion-reduce:` або гейтити
  `prefers-reduced-motion` — глобальний kill-switch у globals.css є, але
  трансформи в утилітах треба знімати явно
- Easing для «дорогих» переходів — `cubic-bezier(0.19,1,0.22,1)`, тривалість
  300–500ms; різкі 150ms лишати тільки для `active:`
- Анімувати лише `opacity`, `translate`, `scale`, `box-shadow`, колір —
  нічого, що спричиняє reflow

**Інтерактивні стани**
- Hover ТІЛЬКИ на тому, що справді реагує на клік: посилання, кнопка, картка,
  яка сама є посиланням. Наведення на текстовий блок, іконку-ілюстрацію,
  логотип-картинку чи картку, всередині якої клікає лише кнопка, — обіцяє
  дію, якої немає, і збиває з пантелику. Секції для читання (напр. «Про нас»
  із колонками переваг) лишаються без hover взагалі
- Якщо для неклікабельної картки все ж потрібен акцент — максимум легка тінь.
  Без трансформацій, масштабування, зміни кольору тексту чи появи меж
- Картки-посилання: підйом або зміна межі/тіні + акцент на заголовку,
  іконка/зображення реагує окремо (scale/translate)
- Кнопки — тільки `ButtonLink`/`SubmitButton` з `@/components/ui/Button`
- `focus-ring` на кожному інтерактивному елементі

## SEO
- Кожна сторінка має свій метадані-блок (title, description, OG image) через Next.js Metadata API
- Значення брати з <head> відповідного файлу в /legacy-export
- 404.html → not-found.tsx, 401.html → окрема сторінка/обробка помилки доступу

## Форми
- Форма Contact Us (contact-us.html) наразі відправляє заявки на email
- У Next.js реалізувати через API route (/src/app/api/contact/route.ts) + Resend (resend.com) для відправки email
- Потрібно: зареєструвати акаунт на Resend, отримати API key, додати в змінні середовища (.env.local, і пізніше в Vercel Environment Variables)
- Email-адресу отримувача заявок — уточнити у користувача

## Процес перенесення сторінки
1. Відкрити відповідний .html з /legacy-export
2. Витягнути контент, структуру секцій і метадані (title/description/OG)
3. Зверстати заново на Tailwind: точно перенести контент і функціонал, виправити
   проблеми верстки і одночасно застосувати покращення з розділу "UX/UI покращення"
4. Перевірити адаптив на mobile/tablet/desktop
5. Коротко пояснити користувачу, що саме було виправлено/покращено порівняно з оригіналом

## Мультимовність (i18n)
- Мови: UA (основна/дефолтна) та EN
- Реалізація: next-intl, маршрутизація /uk/... та /en/... (або /  для uk як дефолт + /en для англійської)
- Контент: увесь текстовий контент зберігати у файлах перекладів (messages/uk.json, messages/en.json)
  або як частина об'єктів у /src/content для каталогу/блогу
- EN-версія контенту — автоматичний переклад (без ручної вичитки), якість "достатньо для розуміння",
  без вимоги ідеальної редактури
- Перемикач мов (LanguageSwitcher) — перемикає URL на відповідний locale, без зовнішніх скриптів
  (Weglot видалено з проєкту)
- SEO: hreflang теги для uk/en версій кожної сторінки
